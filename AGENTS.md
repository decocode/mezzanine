# Agent instructions

This repository is Mezzanine, a React Aria design system by DecoCode Ltd. It contains the component library (`@decocode/mezzanine`) in `src/` and the documentation site for mezzanine.fly.dev in `site/`. The Lab, an experimental sandbox, is in `site/lab/`.

## Commands and when you are done

- `npm run dev` starts the site.
- `npm run check:rules` checks the project rules. Run it before finishing any code change.
- `npm run lint` and `npm run build` run when library, site or configuration code changes. `npm run build` builds both the package and the site.
- `npm run test:e2e` runs the browser tests. Run the tests that cover what you changed, such as keyboard, motion, themes or responsive layout. Run the wider suite when shared foundations change, such as tokens, motion or shared styles. A text-only edit does not need it.
- Scan staged changes with `gitleaks git --staged --redact .` before a commit. The configured hook does this.
- Do not run Lighthouse unless the user asks. If asked, run it once, report the results, and remove only disposable report files generated by that run. Preserve pre-existing reports and any reports the user asks to keep.
- Complete the requested change and check that it behaves as intended. Run the relevant checks and fix failures your change caused. Report any remaining failures and any checks that could not run, and say why. If the work is finished but a check is missing, say that clearly.
- Do not create a commit unless asked. Leave unrelated changes alone.

## Read what the task needs

- `MAP.md` has the file layout. Read it when you add, move or remove files, and update it when you do.
- `README.md` is a short introduction for people visiting the repository on GitHub. Keep it that way: no component guidance, migrations or change notes.
- `src/docs/COMPONENTS.md` explains how apps use the components. Update it when a component's usage changes.
- `site/PAGES.md` explains how documentation site pages are built.
- `docs/MISSIONSTATEMENT.md` explains the purpose of Mezzanine, who it is for and the principles behind it. Read it for product, design, naming and documentation-structure decisions, and when you propose ideas. A small fix does not need it.

`docs/` is private and gitignored. `docs/MISSIONSTATEMENT.md` exists only on the user's own computer. Do not commit it, copy it into tracked files or quote it in public content. If you cannot find it, tell the user and continue.

## Resolving rule conflicts

- Follow the user's instructions and satisfy accessibility, the library/site/Lab boundaries, React Aria conventions and scope limits together.
- Honour explicitly approved exceptions.
- A broad task request does not by itself waive a specific approval boundary.
- If a real conflict remains after checking the context and existing approvals, explain it and ask the user.

## Working with the user

- Lead with the result. Keep reports short and in plain English, and explain any jargon.
- When you introduce a CSS or engineering idea, explain it in one or two sentences.
- After a change, say what each changed file does, why it changed, and how you checked it. List notable private helpers you added.
- You are authorised to do routine implementation, investigation and checking within an agreed task. Do not ask permission for these.
- Fix your own mistakes, such as a wrong test selector, and mention them in the report.
- Ask about unresolved material design decisions, new public names that need approval under the Names rules below, changes to agreed rules, or conflicting requirements. Ask at most three questions at a time. Offer options when useful, and say which you recommend.
- While you wait for an answer, continue independent work that does not depend on it.
- A request or an approved proposal already covers what it names. Do not ask for the same approval twice.

### Names

- The user decides new public names. Propose each one with a one-line reason and wait for approval. Batch several names into one question.
- Within an approved task, using the exact name of the corresponding React Aria component (for example `Switch`) needs no separate naming approval. This does not authorise adding unrequested components.
- Public names are the ones consuming apps rely on: exported components, hooks, functions, props and types; token names; and documented data attributes and class names. Internal class names and private helpers need no approval.
- If an approved name seems wrong, say so and keep using it until the user decides.
- Don't use a CSS term with a different meaning. A name that is also a CSS word (a property, value, keyword or concept, such as `columns`, `grid`, `inline`, `block`, `container` or `layer`) must mean the same thing as in CSS. This covers public names, documentation and Lab page titles, and explanatory copy. Using a CSS word with its CSS meaning, such as `gap`, is encouraged.

## Ideas and the approval process

The user welcomes ideas from agents, including unusual ones: new ways of working, best practice, the latest technologies, and anything that saves time, money or effort or makes the work more joyful. Explain ideas in plain English, and check them against `docs/MISSIONSTATEMENT.md`. Ideas follow these steps, in order:

1. **Talk it through.** Present the idea to the user in conversation first.
2. **Write a proposal, if it is formal enough.** Proposals are Markdown documents in `docs/`. The user decides when an idea is ready for one.
3. **Experiment in the Lab.** Build in `site/lab/` only after the user says to start.
4. **Promote only with approval.** When an idea looks viable, the user decides whether it moves into `src/` or the documentation site.

Do not put an idea into code, in the Lab or anywhere else, before the user has agreed to that step.

## Stack

- Use React with TypeScript and `react-aria-components`. Keyboard, focus, pointer, touch and accessibility behaviour come from React Aria in both the library and the site.
- Avoid `useEffect`, `useLayoutEffect` and `useInsertionEffect`. Use an event handler, a calculation during rendering, `useSyncExternalStore` or a ref callback. `npm run check:rules` allows only the effects listed, with reasons, in `scripts/effect-rules.mjs`. Adding to that list needs the user's agreement.
- Use npm, and keep `package-lock.json` in sync with `package.json`.
- Keep configuration minimal and follow the existing Vite and Oxlint setup.
- Make only the requested change and the smallest changes needed to make it work. Do not add speculative features, sample content, dependencies or abstractions.
- Give each file one clear responsibility. Use literal, descriptive names. Create a new folder or shared module only when the current work needs it.

## Library, site and Lab boundaries

### Library (`src/`)

- `src/` is the package. Everything a consuming app can use is exported from `src/index.ts`. Do not import from `site/` inside `src/`.
- `react`, `react-dom` and `react-aria-components` are peer dependencies. Do not bundle them. If library code imports another package directly, list it in `package.json`.
- Library components contain no product-specific content, branding, copy or imagery.
- The library owns each component's anatomy, appearance, states, motion and behaviour. A consuming app, including the site, supplies content and a theme and positions components in its own layout. If a consumer has to re-add library class names, attach special slots, restyle internals or reimplement behaviour, the component's recipe belongs in `src/`. Move it there and tell the user.
- A thin re-export of a React Aria component is acceptable until Mezzanine has designed that component. Once it is designed, build the recipe in `src/`.
- Assess compatibility when changing supported public contracts, including exported components, hooks, functions, props, types, tokens, and documented data attributes or CSS classes. Call out removals, renames and incompatible changes as breaking changes, and describe them in the commit message with a `BREAKING CHANGE:` footer. Additions and internal implementation changes are not automatically breaking.

### Tokens and motion

- Component CSS takes design values from tokens (CSS custom properties), rather than defining its own literal values. That covers colour, font, size, spacing, radius, shadow and motion. Token and theme definition files supply those values. Structural and semantic values are fine: `0`, `100%`, `auto`, `inherit`, `currentColor`, `transparent` and similar. Consuming apps may use Mezzanine's supplied themes or override token values in their own theme files. Name tokens by purpose, not appearance (`--color-accent`, not `--color-yellow`).
- Text follows the type scale in `src/docs/TYPOGRAPHY.md`. Component CSS sets one complete role (font family, size, weight, letter spacing, line height and text transform) chosen from its Pattern mappings, and state rules change only the weight, to `--font-weight-default` or `--font-weight-emphasis`. Product and site markup use the `mz-text-*` classes. `npm run check:rules` enforces this for components.
- Take durations, easing, travel distances, entry scale and non-zero rotation angles from the shared motion tokens, not per-component numbers. Plain endpoints that mean "none" or "full" (opacity 0 or 1, scale 1, translate or rotate 0) and static centring offsets can be written directly.
- Reduced motion has two sources. The user's system setting applies in every theme and area, and nothing overrides it. The Wireframe theme also suppresses motion by default, but only in the area showing Wireframe, not sibling areas showing another theme. An explicitly nested Light, Dark or System area restores normal motion unless system reduced motion applies. Every component with motion honours both sources. New motion is not finished until it does.
- Loading and progress indicators keep their state visible when motion is reduced. Whether such an indicator may keep moving is decided with the user, indicator by indicator.

### Layout and stacking

Agreed by the owner on 18 October 2026.

- Components respond to their container, not the screen. Use container queries for layout changes. Where the rendered structure itself must change (for example inline panel or drawer), measure the container with a ref callback or `useSyncExternalStore`. Media queries describe the person's setup only: preferences such as reduced motion and colour scheme, pointer and hover, display mode, and the outer page layout.
- Stacking order (`z-index`) comes from one shared, named scale in `src/tokens/z-index.tokens.css`: `--z-index-base`, `--z-index-raised`, `--z-index-sticky`, `--z-index-overlay` and `--z-index-toast`. Components choose a step by name and never set their own number; `npm run check:rules` enforces this for library CSS. Every pop-up (tooltip, popover, drawer, dialog) uses the overlay step, and React Aria's opening order puts the newest on top.
- The `mz-ratio-pair` class (named Split, then the RatioPair component, until 20 October 2026) is the layout building block for two areas that share a row in a set ratio and stack when their container is too narrow. AppShell frames an app's screen, with Panels at the start, end and bottom edges that share the space and become drawers when there's no room (agreed 19 October 2026). They replaced Sidebar, which was removed on 20 October 2026; Rail comes next.
- Describe sides as start and end with CSS logical properties (`margin-inline-start`, `inset-inline-end`, `padding-block`). Use left, right, top or bottom only where the meaning is truly physical, with a `physical:` comment on the same line or the line before saying why. `npm run check:rules` enforces this for library CSS.

### Documentation site (`site/`)

- The site imports the library as `@decocode/mezzanine`, not by relative paths into `src/`. It consumes the library the way apps do.
- Build the site from React Aria Components where React Aria provides the pattern. If Mezzanine already exports that component, import the Mezzanine export. A direct `react-aria-components` import is allowed only while Mezzanine has no matching export, and it must not be styled to look like an implemented Mezzanine component.
- Use Mezzanine's exported `Table` parts for comparison matrices and other tables. Use native semantic HTML for static page structure and content that React Aria does not cover.

### Lab (`site/lab/`)

- The Lab is an experimental sandbox, not authoritative documentation or part of the public library. Label experiments clearly as illustrative and unapproved.
- The Lab may use public library exports through `@decocode/mezzanine`. Neither `src/` nor documentation pages, examples, content or shared site components may import or re-export Lab code, styles, data or candidate tokens. Site routing may load the Lab's entry component only to render Lab routes, and navigation may link to them.
- Keep experimental styles and candidate values inside the Lab and scope them so they cannot affect documentation pages. File location alone does not isolate CSS. Do not place them in shared site styles, library tokens or public exports.
- Do not copy or promote Lab code, designs, values or behaviour into `src/` or authoritative documentation without the user's approval for that promotion. The instruction to move component recipes into `src/` does not authorise Lab promotion. After approval, implement and check the feature in the library, export it where applicable, document the real public implementation, and have the Lab use it.
- Lab examples, tests and passing builds do not prove a feature is approved. Written proposals describe Lab experiments as proposals only.

## Documentation accuracy

- `src/` shows what Mezzanine currently contains. The site documents the library. It does not design, extend or simulate it.
- Document only components, variants, states, tokens, behaviours and rules that are implemented and available through the public API.
- If the implementation and an approved requirement disagree, find out which is correct before changing either. Do not document a bug as intended behaviour.
- Before adding documentation, check the implementation and its agreed behaviour. If something is missing or ambiguous, ask the user before defining or documenting it.
- Examples render the real exported components. Do not create documentation-only replicas, variants, styles or behaviours.
- The approved information architecture may include an empty route before its subject exists. That page says `Not implemented`, has no speculative examples or rules, and is marked `WIP` in navigation. An empty route is not evidence that its subject exists.
- Show token values from the token source. Do not copy values by hand into site code.
- Use descriptive teaching labels in examples, such as `Toggle A`, `Column A` or `Current page`. Use realistic product copy only when it is needed to demonstrate agreed behaviour. Sample text must not imply that an unimplemented feature exists.
- When React Aria names a component part or concept, keep that exact term in code references and API explanations. Readable labels such as "Navigation tree" are fine when the page gives the exact React Aria name in code and links to the official React Aria page.
- If written documentation disagrees with the implemented library, investigate, then correct whichever is wrong.
- Present a foundation or component as documented only after it has been agreed, implemented, exported where applicable, and checked.

## React Aria alignment and naming

- React Aria Components is the behaviour and naming foundation for Mezzanine's atomic components. Before implementing or revising one, check the resolved version in `package-lock.json` or the installed package and consult compatible official React Aria documentation. The range in `package.json` is not the resolved version. Do not make unrequested dependency upgrades as part of a documentation or component change.
- When a Mezzanine atomic component corresponds to a React Aria component, use the exact React Aria name for the export and the file (`ToggleButton`, `ToggleButtonGroup`, `Toast`, `Table`, `Switch`, `Slider`). Documentation titles and navigation may use readable labels, as described above.
- Compose the same documented React Aria parts, and follow its prop names, event names, controlled and uncontrolled conventions, slots, render props, state model, keyboard and focus behaviour, and accessibility semantics. Keep conventions such as `onPress`, `isDisabled`, `isPending`, `isSelected` and `onSelectionChange`. Do not add aliases for the same concept.
- Use the official Vanilla CSS example for the component as the implementation baseline. Keep its anatomy, selectors, documented state data attributes, orientation and placement attributes, interaction-state coverage, forced-colour handling and reduced-motion handling. Express visual values through Mezzanine's tokens, not the example's literal values.
- Preserve the underlying component's documented states and behaviours. This does not mean building a demonstration or new design for every optional feature. If supporting one needs an unresolved design decision, ask the user.
- A deviation from React Aria's name, anatomy, API, selectors or behaviour needs the user's agreement and a documented reason.
- Preserve recorded, approved deviations rather than reverting them to React Aria defaults. Agreed deviation: `TooltipTrigger` defaults to a 500ms hover `delay`, shorter than React Aria's 1500ms default. Do not change it without the user's agreement. Keyboard focus behaviour is unchanged.
- Advanced Mezzanine patterns that compose several primitives can have purpose-based names that the user decides. The user may approve a short name, such as `NavTree` for Mezzanine's composed version of React Aria's `NavigationTree`. The documentation then names the React Aria component it is built on and says when to use which. The underlying atomic parts still use the matching React Aria components. Keep wrapper props close to the underlying component's API, and pass `className` through.
- Treat migrated DecoCode components as input to review, not as the naming authority. Rename or revise them when they conflict with React Aria conventions.

## Button and Link

This is an agreed deviation from the exact React Aria naming and anatomy rules. Do not undo it, split it or work around it without the user's agreement.

In Mezzanine, "button" describes an appearance. Appearance (looks like a button or like a text link) and behaviour (performs an action or navigates) are separate decisions. Browsers and assistive technology treat the two behaviours differently. Navigation supports opening in a new tab and copying the destination. Actions support form submission and activation with both Enter and Space. One Mezzanine component keeps both by choosing the underlying React Aria component from the props.

| Intended use | Mezzanine component | Underlying React Aria component |
| --- | --- | --- |
| Action button | `<Button onPress={...}>` | `Button` |
| Navigation styled as a button | `<Button href="...">` | `Link` |
| Ordinary text link | `<Link href="...">` | `Link` |

- Anything that looks like a button uses the shared `Button`, including calls to action in the site. Anything that looks like an ordinary text link uses `Link`. Do not restyle either by hand to imitate the other.
- `Button` supports text only, a leading icon or a trailing icon, and icon buttons. An icon button always has a label, its children, and `labelPlacement` shows it in a tooltip, below the icon or above it, so the label is also its accessible name. Agreed by the owner on 19 October 2026; `ToggleButton` works the same way.
- There is no separate `IconButton`, and no extra component for navigation buttons.
- Labels and destinations for a Button in the site live in the page's content file, not the page component.
- Button styling is identical whether the element is a button or a link, with no text underline in any theme, Wireframe included.
- If you change the underlying element, check that it renders the right element and works for keyboard and assistive technology.

## Components, accessibility and responsive design

- Target WCAG 2.2 Level AA across the library and the site. Do not claim compliance without checking the finished components and interactions.
- Build mobile first. Check content and controls at 320 CSS pixels, with text enlarged to 200%, and without unintended horizontal page scrolling.
- Use `react-aria-components` for the interactive patterns it supports, including its keyboard, pointer, touch and focus handling. Do not recreate them.
- Use semantic HTML for page structure and static content. Give every control an accessible name, prefer visible labels, and provide text alternatives for meaningful images.
- Keep focus visible. For each finished interaction, check keyboard operation, focus order, screen reader labels, touch target size, colour contrast and reduced-motion behaviour.

## UI and logic files

- Keep `.tsx` files for rendering, component composition, React Aria wiring and local display state. Simple conditions and `map` calls that render UI can stay there.
- Put nonvisual calculations, sorting, transformations and reusable decisions in clearly named `.ts` files. Longer or shared content lists can also live there.
- Move logic out when it is nontrivial, mixes responsibilities or is reused. Keep short, single-use values next to the component that shows them. Avoid a paired `.ts` file for every component and a generic `utils.ts`.
